* DONE Work on FLTKAda reports examples/Fonts.Mod can't record the top left dot
Found 2026-11-05 by FLTKAda, porting FLTK's test/fonts.cxx; recorded
there as FLTK-issues.md F30.

In the vector font editor (F1), a click on the top left dot adds
nothing, so a stroke begun there starts at the second dot. Each
letter's strokes are a row of vec ended by 0X, and a dot is stored as
column * 8 + row, so the top left dot is 0X too. AddCmd finds the first
0X, writes the dot's 0X there, and the row is unchanged. fonts.cxx has
the same bug (add_point_cb, vec[255][128]), which Fonts.Mod copied.

The saved table (SaveCB) is a C string per letter, so a 0 inside one
would end it. FLTKAda's port leaves the dot out on purpose, with a
comment; a fix that records it would need another encoding, such as
storing column * 8 + row + 1, for both the editor and the saved table.
Not checked in pofltk itself: this is from reading Fonts.Mod, which
shares fonts.cxx's encoding.

Done 2026-11-06: confirmed, and fixed by storing each command plus 1;
the saved table leaves the dot out, with an alert (doc/fltk-issues.md,
146).

* TODO Work on FLTKAda reports FlGl.DrawImage reads past its data
Found 2026-11-12 by FLTKAda, sorting its guards (FLTKAda-BUGS.md 28);
recorded there as FLTK-issues.md F40. Since 2026-11-12, doc/fltk-issues.md
170 (until then this said it wasn't there).

FLTK's gl_draw_image (src/gl_draw.cxx:236-244) passes
d < 4 ? GL_RGB : GL_RGBA to glDrawPixels, so depths 1 and 2 are read
at three bytes a pixel, and it leaves GL_UNPACK_ALIGNMENT at 4, so a
row whose length in bytes isn't a multiple of 4 is taken as padded.
Either way it reads past data of exactly w * h * d bytes, and draws
the wrong colours: grey as RGB, and such rows askew. A scratch C++
program under Xvfb and valgrind, drawing a malloc'd w * 10 * d bytes:
depth 3 at width 8 and depth 4 at width 10 were clean; depths 1 and 2
at width 8 had 107 invalid reads each, and depth 3 at width 10 had 12,
all in Mesa's glDrawPixels.

FlGl.DrawImage (src/gl/FlGl.Mod:517) checks w * h * d <= LEN(data)
and documents depth 1 as gray, then calls ofl_gl_draw_image
(src/gl/FlGl.cpp:281), which calls gl_draw_image, so it has the same
over-read. FLTKAda's fix (body/c_fl_gl.cpp, fl_gl_draw_image) draws
the image itself: it saves GL_UNPACK_ROW_LENGTH, GL_UNPACK_ALIGNMENT,
GL_UNPACK_SKIP_ROWS and GL_UNPACK_SKIP_PIXELS, sets them to w (or
ld / d), 1, 0 and 0, calls glRasterPos2i and glDrawPixels with
GL_LUMINANCE, GL_LUMINANCE_ALPHA, GL_RGB or GL_RGBA for depths 1 to 4,
and restores them. FLTKAda's test/unit/test_gl_draw_image.adb reads
back what each case draws. Not checked in pofltk itself: this is from
reading FlGl.Mod and FlGl.cpp.
